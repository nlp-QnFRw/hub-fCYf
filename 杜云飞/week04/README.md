## 1. 前两版：语料是怎么一步步换掉的

> 本节是**演进记录**，不是当前配置。当前在用的是第三版小说语料（第 14 节）。
> 两版的语料 txt 和模型权重都已删除，这里只留数字和结论——
> 它们解释了"为什么最后不用维基，而用小说"。

第一版直接用第四周那份 21 万字的财经新闻语料。它能跑出漂亮的 PPL（53.7），但一上手就露馅：

```
输入「黄金」→ ★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★……
输入「国庆」→ ★★★★★★★★★★★★ 10月506 -8月270 2.4027 0.0307 0.5950 0.0000 2000年大重合……
```

`★` 在 21 万字里只出现 **41 次**。模型被问到"黄金"时实在不知道该接什么，
于是一路抽到了词表尾部这些几乎不出现的字符——**这不是 bug，是"没见过"的表现**。

根因有三条，全部指向数据：

| 问题 | 数字 | 后果 |
| :--- | :--- | :--- |
| 语料太小 | 21 万字 / 8M token 预算 = **37 个 epoch** | 模型在"背"而不是"学"，验证 loss 20 epoch 后就反弹 |
| 领域太窄 | 全是财经新闻，2988 篇 | 出了金融词汇就没有第二选择，只能抽低频字符 |
| 数字噪声大 | 数字占 8.5% | 模型花大量参数去学"随机数"，学不到任何规律 |

### 第二版：换成中文维基百科

**中文维基百科**（`pleisto/wikipedia-cn-20230720-filtered`，25 万条目 / 501MB JSON）。
选它的理由：句子规范、领域宽、事实密度高，而且它是**人类写给人看的说明文**——
这正是 base model 该学的东西。

当时的清洗流程（脚本已随语料一起删除，这段留作记录）：

```
501MB JSON（25 万条）
  → 流式抽取 completion 字段（不一次性 json.load，省 1~2GB 内存）
  → 去控制字符 / URL / 重复空格
  → 按段落切，超长段在句号处断开（配合 block_size=512）
  → 丢掉日文假名、俄文等夹杂 >12% 的行
  → 丢掉符号/数字占比 >45% 的行（表格残留、坐标列表）
  → 段级去重
= 100M 字符 / 78.6 万段 / 261MB txt
```

字符集 15368 个，但**频次 < 30 的 8313 个加起来只占 0.05%**——
用 `--min_freq 100` 把它们映射成 `<unk>`，词表压到 **5339**，
embedding 省下 1/3 参数，采样时也不会再抽到"一辈子没见过两次"的字。

### 换语料前后，同一批输入

| 输入 | 21 万字新闻模型 | 1 亿字维基模型 |
| :--- | :--- | :--- |
| `黄金` | 融出了一次分红。 | ，以及在1962年至1974年之间，由于英国铁路的经济衰退和发展，美国铁路曾是美军所要求的重要性。 |
| `今天天气不错` | 在新基金的为中国投资者一种。 | ，就在天气里，天气不断降落。一个月后，天气在月球轨道的形成和发展下逐渐消失。 |
| `国庆` | 封A市场人士表示，一部分析师称，其中期货市场的主题将发展…… | 祝节，在1962年8月4日到8日在马来西亚新加坡举行。1973年9月20日起，该项目由广东省政府主办。 |

**语法从"勉强能读"变成"完全通顺"，`★★★` 崩坏消失**——
但请注意右边那列的内容仍然是编的。这是 16M 参数的硬上限，第 11 节会算给你看。

> **维基版又为什么被换掉**：它只能写百科腔。维基里没有对话、没有情节、没有"接着往下讲一个故事"
> 这种文本，所以你问它"北京有什么好地方"，它只会把问题当成一个条目的开头，接着写"某某是某某"。
> 第三版因此换成小说——**小说是唯一一种"续写本身就是正确任务"的语料**，见第 14 节。

## 3. 网页对话台：把它点成一个能聊的东西

```bash
python chat.py            # 自动开浏览器，默认 http://127.0.0.1:8000
python chat.py --port 9000 --no-browser
```

界面是 DeepSeek 那一套：左侧会话列表、右侧气泡、流式逐字吐、底部参数抽屉可以边聊边拉
温度 / Top-P / Top-K / 重复惩罚。**没有 Flask、没有 FastAPI，后端只用了 `http.server` 和 PyTorch。**

### 先说清楚它是什么

默认模式是**续写**，不是对话。原因我实测过：给它对话格式，它接成这样——

| 喂给它的开头 | 它接出来的东西 |
| :--- | :--- |
| `用户：北京为什么是首都？\n助手：`（对话模式） | 你好也。」在这一天晚上，他们告诉一名玩家是怎么的，只有一辆玩家要使用任何一人…… |
| `问：黄金价格为什么上涨？\n答：`（续写模式） | "你们只能回去，也不要回到呢？"。当时黄金一路，黄金用"那里得知我们这样的事情…… |
| `北京是中华人民共和国的首都，`（续写模式） | 为中华人民共和国最大的国际经济性发展基地之一，位于北京市南区南街57号…… |

前两条一眼就能看出问题：**它把"问答"当成了一个故事的开头**，直接跳到小说对白和叙事，
完全没意识到自己该"回答"。第三条虽然是编的，但文体对——百科腔、句法通。

维基百科里没有"问答"这种结构，所以它学不到对话的统计规律。
**`助手：` 三个字对它只是个噪声标记**，接出来的东西反而更乱。
所以默认走续写，顶部黄条把这件事写在明面上，不假装自己是聊天助手。

### 两个绕不开的工程问题

**① 它写完一段就收尾。** 这其实是模型学对了：维基每段都有明确结尾，
所以给它一句不完整的话，它写完一个完整段落就吐 EOS。实测上面那句在 **44 个字符**处停下：

```
北京是中华人民共和国的首都，位于中国西北部，北临济南，东接天津滨海新区，面积72.34平方公里。是该省的第三大城市。← 到这里出 EOS
```

想让它继续写，就在采样时把 EOS 的 logit 压成 -inf
（`model.py` 里 `filter_logits(..., ban_ids=[EOS])`）。参数面板里"允许模型自己收尾"的开关就是它——
**关掉它才会一路写满长度，打开它你能看到模型"觉得自己写完了"的那个瞬间。**

**② 上下文只有 512 个字符。** 多轮拼起来很快就满。后端从**末尾**往前截断：
宁可丢掉最早的几轮，也要保住当前这一问。每条回复下面那根细进度条显示的就是
`本轮 prompt 占用 / 512`，涨到橙色就该开新会话了。

### 参数拉到两端会发生什么（同一句话，只改 temperature）

```
prompt：北京是中华人民共和国的首都，

T=0.5  位于中国北京市，是中国第一个以现代化的城市。
T=1.0  2014年3月，该市场正式改组时名为"中华人民共和国城市聚居区"，由中央人民政府筹备，
       是该区的八座建筑群之一，面积15000平方米……
T=1.5  乘夜日运览著大通舆绯闻。除了此时山蛋拜参马援忙，五朝城地聚宫还设计怪木器了。
       拔、莫帜丞蒲阪齐国八王建立独族社会科法国墙身……
```

T=0.5 保守但平淡，T=1.0 开始编造细节，**T=1.5 直接退化成乱码**——
高温把词表尾部那些概率接近 0 的字符全放了出来。这就是讲义里"温度是熵的旋钮"最直观的样子。

### 顺手写在里面的几个教学点

| 位置 | 对应讲义知识点 |
| :--- | :--- |
| `POST /api/chat` 逐字符 `data: {...}` 推送 | 06 节流式输出：TTFT 之后每来一个 token 就 flush 一次 |
| 生成中按停止 → 服务端写 socket 抛 `BrokenPipeError` → 下一个 token 就退出循环 | 真实推理框架的 `abort` 就是这么实现的 |
| 每条回复下面的 `字数 · 字/秒 · 上下文 x/512` | 把 TTFT / 吞吐 / 上下文窗口三个指标摆在眼前 |
| 参数抽屉里每个滑块的说明 | 04 节采样策略的副作用（温度↑ 发散、惩罚↑ 抑制复读） |
| 对话模式在生成到 `用户：` 时停止 | 大模型的 stop strings 机制 |

> 单文件说明：`chat.html` 内嵌了全部 CSS/JS，没有任何 CDN 依赖。直接双击也能看界面，
> 只是连不上后端时会进"演示模式"（用固定文字模拟流式），方便你先把 UI 摸一遍。

## 5. 模型规格：为什么是 16M

```
层数 8 · d_model 384 · 6 头 × 64 维 · SwiGLU(hidden 1024) · 上下文 512
RoPE 位置编码 · RMSNorm(Pre-Norm) · 全部 Linear 无 bias · Embedding 与 lm_head 共享权重
参数量 16,212,480（词表 5339 比老版 2576 大，embedding 多了 1M）
```

选型先测吞吐（RTX 5050 Laptop 8G / bf16 / seq 512 / 词表 5339 / 训练态含优化器）：

| 配置 | batch | 参数量 | 吞吐 | 训练峰值显存 |
| :--- | ---: | ---: | ---: | ---: |
| tiny 4层/192 | 32 | 2.80M | 270k tok/s | 1.7G |
| mini 5层/240 | 32 | 4.74M | 165k tok/s | 2.1G |
| small 6层/288 | 32 | 7.51M | 117k tok/s | 2.7G |
| **base 8层/384** | **32** | **16.21M** | **66k tok/s** | **4.0G** |
| large 10层/480 | 16 | 30.22M | 26k tok/s | 6.4G |

> large 必须把 batch 砍到 16，否则 8G 显存会用共享内存兜底，速度掉一个数量级。
> base 用 32 时还有余量，是这张卡上的"刚好"。

在 1 亿字语料上，Chinchilla 的经验最优（20 token/参数）指向 5M 左右；
但我们要的是**在 50 分钟内把 PPL 压到最低**，而不是算力最优，
所以选 16M 跑 200M token（≈12 token/参数）——偏"过参数化"，
代价是多花算力，收益是同样时间里 loss 更低。

几个值得盯住的细节：

- **Greedy 8 个字后就开始复读**，因为"距离北京市区约10公里"是局部最优。
- **T=1.5 直接崩成乱码**，而 T=0.5 虽然通顺但永远只说最保险的话。

## 8. 规模对照：Scaling Law 的成立与失效

```bash
python scaling.py --tokens 8e6 --with-lstm
```

> ⚠️ **这一节的实验是在老的 21 万字新闻语料上做的**，图在 `docs/scaling.png`。
> 保留它是因为它示范了"数据上限"这件事；换成 1 亿字语料后，最优点会明显右移，
> 结论不能直接搬——**这正是 Scaling Law 最容易被误用的地方**。

固定 8M token 预算，只改参数量：

| 规模 | 层数/d_model | 参数量 | best val loss | val PPL | 训练 loss（结束） |
| :--- | :--- | ---: | ---: | ---: | ---: |
| tiny | 4 / 192 | 2.27M | 4.198 | 66.6 | 4.01 |
| mini | 5 / 240 | 4.08M | 4.032 | 56.2 | 3.70 |
| **small** | 6 / 288 | 6.72M | **3.946** | **51.8** | 3.33 |
| base | 8 / 384 | 15.15M | 4.000 | 54.6 | 2.28 |
| large | 10 / 480 | 28.89M | 4.099 | 60.3 | 1.45 |
| **LSTM 对照** | hidden 768×3 | 15.96M | 4.249 | 70.1 | 3.73 |

- **最优点在 6.7M**，再大就一路变差：训练 loss 还在暴跌（2.28 → 1.45），验证 loss 已经反弹。
  21 万字撑不起 15M 参数，这就是 Chinchilla 强调"参数和 token 必须同步扩"的原因。
- 小段幂律拟合 **L ≈ 9.70 · N^(-0.057)**（α≈0.057，讲义参考值 ~0.076，同一量级）。
- **LSTM 给了 5 倍 token 也只到 PPL 70.1**，差距在结构不在参数：
  隐状态是固定大小的信息瓶颈，注意力能直接看到任意历史位置。

## 9. 加餐：KV Cache 到底快多少？（结论反直觉）

```bash
python sample.py --bench
```

| prompt 长度 | batch | 无缓存 | 有缓存 | 加速 |
| ---: | ---: | ---: | ---: | ---: |
| 16 | 1 | 825ms | 922ms | **0.9×（反而更慢）** |
| 128 | 1 | 813ms | 981ms | **0.8×** |
| 400 | 1 | 804ms | 981ms | **0.8×** |
| 16 | 8 | 1044ms | 928ms | 1.1× |
| 128 | 8 | 1906ms | 948ms | **2.0×** |
| 400 | 8 | 3016ms | 1006ms | **3.0×** |

- **batch=1 时缓存反而慢 10~20%**：16M 的小模型喂不饱显卡，每步耗时由 kernel 启动开销决定，
  跟"算了多少 token"无关；缓存还要多付 `torch.cat` 拼接的代价。
  注意无缓存那一列的耗时几乎不随 prompt 变长而增加（825→813→804），说明算力根本没被打满。
- **batch=8 时收益随长度线性放大**：prompt 400 已经到 3.0×，而且无缓存那列飙到 3016ms——
  这才是缓存要解决的问题。
- 放到 7B 模型 + 长上下文 + 高并发，这个差距会变成 10 倍以上——
  这就是 vLLM / TensorRT-LLM 把 KV Cache 当第一优化项的原因。

缓存要显存：序列越长、并发越高，KV Cache 越大，所以才有 MQA / GQA 这些"少存几份 K/V"的技术。

## 11. 它"像"大模型的地方，和"不像"的地方

**像（本质上的像）：**

1. **同一个训练目标**：next-token prediction，没有第二个 loss，全部能力都从"猜下一个字"长出来。
2. **同一套结构**：Causal Mask → RoPE → 残差 → RMSNorm → SwiGLU，和 GPT/Llama 一模一样，只缩小了 100 倍。
3. **语感是真的**：标点、引号配对、"年/月/日"的顺序、书名号的使用，全对。没有一行规则代码。
4. **文体是真的**：给一句"XX 是……"，它会用标准百科腔往下写，
   "位于……，面积……平方公里，2014年3月，……批准为……"——这个模板它学得很准。
5. **重复退化真实存在**：Greedy 八个字后开始复读，T→0 时尤其明显。
6. **会停**：`<eos>` 让它在"这段写完了"的地方停下。
7. **熵随温度变化**：第 7 节那张 T=0.5/1.0/1.5 的对比就是"温度是熵的旋钮"。

**不像（诚实边界）——最重要的部分是这一条：**

| 能力 | 大模型 | 这个模型 | 原因 |
| :--- | :--- | :--- | :--- |
| **事实性** | 有世界知识 | **几乎为零，且会自信地编** | 见下方估算 |
| In-Context Learning | 给几个例子就能做新任务 | ≈0 | 讲义 03 节：ICL 在 ~100B 参数才涌现 |
| Chain-of-Thought | 多步推理 | 无 | CoT 是更大模型才有的涌现能力 |
| 长程连贯 | 能写完整长文 | 2~3 句后开始漂移 | 16M vs 175B 参数，512 上下文 |
| 指令遵循 | SFT/对齐之后 | **完全没有** | 我们只做了预训练 |
| 对话 | 天然会 | 不会，`助手：` 对它只是噪声 | 维基里没有对话文体 |

**为什么 16M 装不下事实？算一笔账：**

- 16.21M 参数 × 2 字节（bf16）≈ **32MB**。
- 1 亿字中文维基，去掉冗余后信息量大约几十 MB。
- 参数里还要分一大块给语法、词形、句式——留给"事实"的可能只有几 MB。
- 所以它记住的是**文体和模板**，不是**内容**。

它写"北京位于北京市东城区西北部，距离北京市区约10公里"——
句式完美，事实上是拿几个高频地名碎片拼的。**这不是模型坏了，这是规模不够。**

> 一句话：**机制对了，规模差 4 个数量级。**
> 用 `python sample.py --interactive` 聊两句，你就能亲手确认：
> 语法是学来的，知识是要用参数量买的。

## 13. 想把"像"变成"更像"

按性价比排序：

1. **继续加数据**（收益最大且不用改代码）：1 亿 → 10 亿字，PPL 能进 15 以内。
   中文维基全量约 3 亿字，加上新闻/百科/书籍混料更好。
2. **换 BPE 分词器**：现在"一个汉字 = 一个 token"，BPE 能把常见词压成 1 个 token，
   同样 512 的上下文能装两倍信息，PPL 会显著下降。
3. **加长上下文**：`--seq_len 1024`，RoPE 表会自动扩展（`_refresh_rope`）。
4. **加参数**：29.9M 的 large 在 1 亿字语料上应该还能再降，代价是 2 倍训练时间。
5. **SFT**：几百条（指令，回答）对 + `labels=[-100]*len(prompt)+...`，
   就能把它从"接龙器"变成"问答助手"。但这超出本周要求——本周只做预训练。

### 14.2 这一版的训练账

| 指标 | 维基版 | **小说版** |
| :--- | :--- | :--- |
| 参数 | 16.21M | 16.14M |
| 语料 | 1 亿字 | 8000 万字 |
| token | 2.00 亿（2 epoch） | **2.97 亿（3.7 epoch）** |
| tokens/参数 | 12 | **18.4** |
| 墙钟 | 49.1 min | **51.4 min** |
| val PPL | 19.83 | **19.74** |

PPL 看着只差一点，但**两者的 PPL 不可直接比**：小说文本的熵远高于百科
（同一句话有无数种合理说法），同样 PPL 意味着模型学到了更多种表达。
对照证据是同一时期的数值：维基版前 3 分钟 val PPL 已经降到几十，
小说版前 3 分钟还是 70 上下。

### 14.3 关键：tokens/参数 才是"训练够不够"的指标

Chinchilla 的结论是每个参数吃 20 个 token。第一版新闻模型只有
**0.5 token/参数**（800 万 token / 16M 参数），这才是它生成 `★★★★` 的真正原因——
不是"过拟合背原文"，而是**严重欠训练**，模型对任何字都没有稳定估计，
只能坍缩到最省力的重复。这一条能省掉很多弯路。

### 14.4 工程加速：torch.compile 让吞吐 +57%

跑训练前先做了一轮吞吐对照（`--seq_len 512`，同一份语料）：

| 配置 | 吞吐 | 显存峰值 |
| :--- | :--- | :--- |
| eager，batch 32 × accum 2 | 72.8k tok/s | 3.79 GB |
| eager，batch 64 | 63.7k tok/s | 7.22 GB |
| eager，batch 96 | 12.2k tok/s ❌ 显存换页 | 10.72 GB |
| eager，batch 128 | 6.7k tok/s ❌ | 14.22 GB |
| **compile，batch 32 × accum 2** | **114.9k tok/s** | **2.73 GB** |

三条结论：

1. **加 batch 不是提速手段**。8GB 卡上 batch 32 已在上限区间，96 起步就撑爆显存，
   WDDM 把显存换到内存后吞吐掉 6 倍。
2. **小模型的瓶颈是逐元素算子，不是矩阵乘**。`torch.compile` 把 RMSNorm/SwiGLU/RoPE
   这些 kernel 融合掉，收益接近 60%，而且编译后**更省显存**（缓冲区复用）。
3. Windows 上要装 `triton-windows`（`pip install triton-windows`）才能编译出融合核，
   否则 `torch.compile` 直接报 `Cannot find a working triton installation`。
   另外 triton 读环境变量时按 UTF-8 解码，中文用户名会让它抛 `UnicodeDecodeError`，
   所以 `train.py` 顶部把 `TRITON_CACHE_DIR` 指向了 ASCII 临时目录绕开。

正式训练实测：**61k → 97k tok/s**（97k 已摊掉验证开销），
所以 51 分钟能喂 2.97 亿 token 而不是 1.6 亿。


另一个坑：这颗驱动报的 `clocks.sm` 恒为 `180 MHz`（满频 3090 MHz），
但吞吐是真的，**别拿这个读数判断是否降频**，看 tok/s。

### 14.6 新模型的输出（temperature 0.9 / top_p 0.9 / top_k 40 / rep 1.2）

给 60 字上文之后：

> 民国二十三年的秋天，保定府城外的官道上尘土飞扬。天还没亮，福来茶馆的门板就卸了一半，
> 伙计提着铜壶在桌椅之间来回穿行。老掌柜把茶碗往前一推，说道："**当，只是在下很快就回来了，
> 您坐吧，今晚我们不许再来啦。**"　　看她这样子态度，老掌柜只能点头，又……

对话格式（引号、`说道：`、`　　` 提行、人称轮换）全部正确，
这是维基语料上完全不存在的能力。

### 14.7 一个反直觉的坑：短开头 = 冷启动

同一句 `老掌柜把茶碗往前一推，说道："` 单独喂进去：

> ……说道："**的人物。**"　　"哦？！"小姑娘皱了皱眉头道："你是怎么知道的？"

前几个字是乱的。原因不是模型差，而是**训练与推理的上下文不匹配**：
训练时模型永远看到 512 字连续文本，位置从 0 到 511；推理时只给它 20 个字，
它从没在"位置 20 处信息量这么少"的情况下被训练过。

修法不是改模型，是**给够上文**。界面里加了「随机开头」按钮，一次填 60~120 字，
差别一眼可见。这也解释了为什么很多人觉得小模型"一开口就胡说"——
不是它不会写，是你没给它起跑距离。
